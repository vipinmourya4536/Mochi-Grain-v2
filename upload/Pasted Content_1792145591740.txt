## A few critical rules for your coding agent

These are the guardrails that matter most for this project.

1\. Do not treat a sensor number as ground truth simply because it arrived over Bluetooth. First establish what the ESP32 packet actually represents. Raw ADC counts, calibrated grain moisture percentage, and temperature readings are different kinds of data. Calibration needs evidence from the real hardware.

2\. Never let offline caching masquerade as live sensor monitoring. Mochi can load its interface and past history offline, but fresh measurements require the probe, and the Android service must be designed to receive them.

3\. Do not overwrite the existing deployment to make Capacitor work. The current app uses Next.js standalone output. The Android build must be compatible with its actual runtime requirements, while preserving the existing hosted PWA.

4\. Test one stage before starting the next. In particular, do not attempt to implement native Back handling, remove demo code, redesign History, add native BLE, and rewrite the build system in one agent run. That is an excellent way to produce a beautiful interface with three broken subsystems hiding underneath it.

The release goal is simple: Mochi Grain 2.0 should show genuine hardware data, explain risks using consistent rules, work offline wherever technically possible, and alert the user reliably without needing the dashboard to remain open. 🌾
